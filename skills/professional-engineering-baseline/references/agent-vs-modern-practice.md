# Agent 与现代工程团队的差异

这份对照用于校正行为，不用于贬低 Agent。成熟工程师也会犯错；差别在于团队把常见失败转成结构、自动化和复查，而 Agent 容易把一次成功的局部执行当成整体完成。

## Agent 的相对优势

- 能快速读取大量源码、Issue、日志和历史记录。
- 能跨模块追踪调用链，提出通常不易发现的关联和缺口。
- 能把重复操作脚本化，并在同一轮覆盖多个受影响的消费者。
- 能在上下文丢失时依据结构化记录恢复任务。

这些优势只有在工程纪律约束下才会稳定转化为交付质量。

## 稳定差异

| 维度 | 成熟工程团队默认 | Agent 常见默认 | 必须补上的动作 |
|---|---|---|---|
| 事实起点 | 当前 trunk、明确版本和环境 | 当前目录、记忆、旧 worktree | fetch 集成基线、读回 SHA、检查现场 |
| 分支 | 短分支、小 PR、频繁集成 | 长分支、旧基线、积压修正 | 开工记录 base，评审/合并前 rebase |
| 变更边界 | 一个结果、一个可审 diff | 修一个点时顺手改多个面 | 先写结果/非目标，按影响面拆分 |
| 验证 | 自动化矩阵绑定准确候选 | 一条测试命令或局部截图 | 按 claim 选层，证据绑定 commit/环境 |
| 审查 | 高风险有作者以外的人查候选，普通变更也留取证词 | 自述已检查，或只看计划 | 记录作者审查；按风险补独立审查 |
| 集成 | merge queue/required checks | 多个独立绿灯后直接交错合并 | rebase、声明基线、合并后 smoke |
| 制品 | 不可变构建、签名、来源 | 从工作树直接构建和安装 | 已集成来源、单调版本、manifest |
| 发布 | 可观测渐进发布和回滚 | 直接替换正式 App/服务 | 锁、candidate 标记、readback、rollback receipt |
| 运维 | 日志、指标、告警、runbook | 运行成功就报完成 | 真实用户入口、故障与恢复证据 |
| 清理 | worktree/临时资源随任务结束回收 | 旧树和脏状态无限累积 | 合并后回收自建干净现场；未知保留 |
| 治理 | 用代码和流水线阻止重复错误 | 新增文档、台账、审批 | 优先自动化门禁，规则保持单一归属 |
| 完成 | `accepted` 才算交付 | 合并/测试通过就宣称完成 | 按 GSE 状态和证据层分开陈述 |

## 本项目中出现过的可核事实

2026-11 的一次真实多 Agent 工程审计显示：旧 worktree 会持续累积，安装回执可能来自未合入的候选，Git 冲突反而很少。问题的共同点是“现场、验证、制品和完成声明没有统一默认”，不是 Agent 缺少某条领域知识。具体项目证据保留在原 Issue，作为案例，不在通用 Skill 中复制。

## 结论

Agent 需要向现代工程师学习的不是“更慢”或“更多审批”，而是：

1. 以 trunk 和当前制品为事实起点。
2. 用自动化验证和真实用户路径证明 claim。
3. 让按风险触发的独立审查、发布门禁、回滚和清理成为默认，而不是事后补救。
4. 用最小机制解决已观察到的失败，不用更多自述和流程堆积掩盖问题。
