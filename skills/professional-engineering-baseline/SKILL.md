# Professional Engineering Baseline

## 强制适用范围

这是 GSE 所有实现类开发任务的默认工作方式，不是可选建议。

在修改代码、配置、测试、构建、安装、部署、运行状态或工程规则前应用本 Skill。完全只读的解释、分析、调研和未落地草稿不需要实现门禁；一旦准备写入或发布，先完成这里的开工检查。

按风险裁剪证据，不要把基线变成形式审批。无法满足某项要求时，说明具体缺口、影响和最小补救，不得用自述“已完成”跳过。

本 Skill 负责 Agent 特有的执行纪律和门禁；生命周期、证据层级、协作和最小充分工程的规范正文仍归 GSE 的各单一归属文档。这里不建立第二套状态库或审批流程。

如果本 Skill 的执行检查与 GSE 规范正文冲突，以对应 GSE owner 为准并修正本 Skill；只有用户或项目明确规定了更严格的强制政策时，才可在对应入口记录并引用该政策，不能把差异留成隐含的第二套规则。

## 先分清 Agent 与成熟工程团队的差别

成熟工程团队的核心不是知道更多 API，而是把正确做法变成默认、可执行、可复查的团队习惯。Agent 常见优势是搜索广、分析快、能跨模块推理和自动执行；常见缺口是把本地现象当成全局事实、把一次成功命令当成完整验证、把合并或测试绿灯当成用户验收。详细对照见[Agent 与现代工程实践的差异](references/agent-vs-modern-practice.md)。

## 1. 开工门

开始写之前必须读回真实起点：

- `git status` 明确已有改动并保留无关内容。
- fetch 后以项目声明的集成基线为起点；通常是 `origin/main`，也可能是项目明确指定的 release/维护 ref。读取部署 commit 和实际 checkout。
- 按项目写入隔离政策选择 Codex worktree、branch 或规范 checkout 串行写入。隔离形式不改变“一个共享现场只能有一个 writer”的要求。
- 新建任务记录 baseline SHA、结果负责人和写入范围。项目允许时优先使用从当前集成基线创建的独立任务 worktree；项目禁止新 worktree 时，在规范 checkout 串行写入。
- 运行项目已有的 worktree/现场检查。当前目录的 HEAD、index、dirty 文件和 remote ref 必须和声明的 base 一致；不要把项目根、旧 checkout 或旧制品自动当成规范来源。
- 接手本人已有的 WIP 时，先核对 owner、base、dirty 范围和退出条件；归属不明或可能覆盖他人工作时，保留现场并从最新基线重开。
- principal/feature branch 或 worktree 超过一个工作周期、基线已明显前进，或无法证明它包含当前声明的集成基线时，先 rebase 并重验；若 rebase 不能安全进行，保留现场并从该基线重开。
- 不把未提交文件、聊天记忆、旧 checkout 或旧构建当规范来源。

## 2. 结果合同（规范归 GSE LIFECYCLE）

用一个最小专业判断区分变更规模：

- **局部小修**：只改一个模块、无共享合同/持久化/安装/安全边界、可逆、能用定向自动检查稳定证伪。
- **完整交付**：跨模块、改变生产行为、共享合同/数据库/权限/安装/发布、涉及真实外部对象或不容易回退；必须使用完整结果合同和更高层证据。

在完整交付开始前记录足够支撑验收的最小合同。以下只是执行时的入场检查，不重新定义 GSE 的 outcome-contract 字段：

- 用户要看到的 `outcome`，而不是只写“改模块”。
- 验收入口、目标环境、可观察结果和失败条件。
- 必须保持的接口、数据、权限、兼容性和运行不变量。
- 真实影响面：源码、测试、构建、配置、持久化、安装、发布、用户旅程和运维。
- 非目标只在会发生范围歧义时列出。

无法说明“怎样才算用户接受”时，先补事实或问必要问题；不要用实现步骤代替结果合同。

## 3. 小步、完整、可维护

- 一次变更只解决一个连贯结果；不要混入顺手重构、无关文案或第二个功能。
- 先寻找现有实现、标准库、官方 API 和项目惯例；只有当前需求、真实失败或硬边界要求时才新增抽象、回退、兼容层或流程。
- 接口变化同时处理 producer、consumer、持久化、迁移和文档；不能只改一端后靠 merge 发现。
- 依赖变更锁定解析结果，核对直接/传递依赖、来源、漏洞和许可证；不因编译通过就接受供应链风险。
- 删除被替代代码、配置、测试和文档；不保留无当前消费者的兼容层。
- 代码可读性、错误语义和可维护性与功能同等重要；不要把复杂状态藏进隐式 fallback、静默 retry 或吞异常。

## 4. 自动化优先验证（规范归 GSE EVIDENCE）

GSE 的证据层级是唯一规范。以下是 Agent 最容易混淆的 claim 到执行检查的索引，不是第二套证据模型：

| 受影响面 | 最低证据 |
|---|---|
| 静态结构、类型、格式 | typecheck、lint、schema 或等价检查 |
| 业务逻辑 | 定向单元/集成测试，优先覆盖原失败和历史回归 |
| 共享合同 | producer 与全部实际 consumer 的双向/no-major-version change 证据 |
| 持久化、迁移和恢复 | 旧/新数据、旧/新版本、失败与恢复路径 |
| 构建和安装 | 干净源码导出、可复现构建、签名/摘要、安装与读回 |
| 运行和用户旅程 | 真实安装/部署版本的准确入口和可观察行为 |
| 依赖、供应链或构建输入 | lockfile、来源、漏洞/许可证和可复现解析 |
| 高风险或不确定行为 | 故障注入、恢复、回滚或独立评审 |

规则：

- 先在最低可靠层证明，再用更高层补齐低层证明不了的部分。
- 证据绑定准确 commit、环境、配置和命令；换候选后刷新受影响证据。
- 测试成本明显时，按 GSE [测试执行策略](../generative-software-engineering/references/test-execution-strategy.md)选择受影响闭包，只复用输入相同的有效通过证据；正式发布或安装仍需从干净来源执行项目要求的完整回归。不得把发布级全量检查变成每次编辑的机械仪式，也不得用“以前测过”跳过输入已经变化的检查。
- 不用全量旧测试掩盖根因，也不以“测试曾经绿”代替当前候选。
- 测试失败先修根因；禁止删测试、放宽断言或用 fallback 取得绿灯。
- 有 CI 时把 required checks 作为合并门；没有 CI 时建立等价的本地检查、单一合并 gate 和合并后 smoke。
- 涉及随机性、时间、并发或外部服务时记录种子、时钟、环境和边界。

## 5. 独立审查（规范归 GSE COLLABORATION/EGM）

审查范围和独立性定义仍归 GSE；本节只补执行时容易漏掉的门。

- 所有会改变生产行为的 PR 要有可复读的代码审查记录。独立于作者的审查在用户或项目要求、共享合同、持久化/迁移、认证授权、安全、安装/发布、生命周期、跨模块或作者无法独立验证时触发；项目已有等价的强制 review 门禁时复用其证据。
- 低风险、单模块、可逆的局部修改可以由结果负责人完成结构化 diff 和定向测试审查，但必须如实写成“作者审查”，不能冒充独立审查。
- 方案 review 按 GSE/EGM 的触发条件执行；代码完成后必须检查 candidate。两者不是每个任务都必须双审，但不能用方案审查替代代码审查。
- 审查输入是稳定候选、原始结果、范围和验收标准。要求审查者给出可验证风险、后果和修正，不收集泛泛意见或风格偏好。
- 作者核实每条发现：修正、以证据反驳或升级真实用户决定。不能默认等待某个特定云评审渠道。
- 自述“我已检查”、同一上下文自问自答和仅看 diff 总结，都不等于独立审查。
- 高风险安全或生产紧急修复若不能先完成独立审查，记录实际风险和必须在何时补齐的 post-incident review；不能宣称完整验收。

## 6. 集成与合并（规范归 GSE COLLABORATION）

写入隔离、集成责任和换手规则仍归 GSE；本节只补合并前必须读回的执行动作。

- 保持短分支；PR 就绪前 rebase 到项目声明的集成基线并重跑受影响检查。
- PR 说明结果、范围、准确 base/head、影响面、共享消费者、发布单元、回滚和未覆盖项。
- 合并前确认 head 仍是已审查、已检查的准确候选；合并后从准确 merge commit 做受影响 smoke。
- 有 merge queue 或等价平台门禁时使用；没有时保持单一集成 writer，不能把多个独立绿灯当成交错合并后的集成证据。
- 冲突解决如果改变语义、接口或测试预期，按新候选重新审查并重验；不能把“冲突已解”当成“行为仍正确”。
- 分支和 worktree 不长期悬挂；合并后按项目规则回收自己创建且干净、无进程的现场。

## 7. 构建、安装和发布

- 只从项目声明的集成/发布 ref 中已合入并冻结的准确 commit 构建正式制品；candidate、hotfix、backport 必须显式标记来源和适用版本，不能冒充正式来源。
- 制品记录源码 commit、构建号、摘要/签名、目标平台和安装 receipt。
- 版本号单调递增；降级必须有明确回退决定和放行证据。
- 同一安装、签名、设备或发布资源只允许一个活跃 writer；安装要有互斥、读回和失败恢复 receipt。
- 高风险功能采用可观测的渐进发布、feature flag 或可关闭路径；明确 kill switch、回滚方式和数据补偿。
- 安装成功不等于运行健康，运行健康不等于用户接受；分别记录。

## 8. 运维与维护

- 新服务或常驻循环必须有日志、关键指标、错误分类、恢复入口和明确 owner。
- runbook 写真实路径、命令、前置条件、验证和回滚；不把猜测写成步骤。
- 故障先保留证据、隔离影响、恢复安全状态，再修根因和补回归。
- 重复出现的同类缺陷升级为结构化修复：自动化门禁、接口约束或测试，而不是继续增加口头规则。
- 依赖、凭据、权限和退役路径保持最小必要；不把凭据或敏感数据写入仓库、日志或普通文档。

## 9. 现场与资源生命周期

- 任务结束不是只关聊天：已合并、已 push、干净且无进程的自建 worktree 要回收；branch 按项目规则保留。
- dirty、未知、暂停或含独有证据的 worktree 不自动删除；先由 owner 分类、归档或导出。
- 定期用项目审计命令列出 dirty/stale/merged-clean worktree；只回收证明已合并且完全干净的树。
- build、install、device、browser、window、database 和 socket 等共享资源按真实资源键串行。

## 10. 完成声明（规范归 GSE LIFECYCLE）

生命周期状态继续使用 GSE 的 `patch_ready → integrated_preview → ready_for_release → released → accepted`，不要另造状态机。面向用户的简要报告可以同时说明：

- `patch_ready`：源码变更和定向证据已稳定。
- `integrated_preview`：准确 commit 已进入声明的集成基线。
- `released`：目标环境已采用准确、不可变制品。
- `accepted`：真实用户旅程或业务结果已按约定验收。

最终回报先给结果，再列已改变、已验证、未完成和真实风险。不得用“链路闭环”“已交付”等无对应证据的词代替状态。

## 11. 禁止的捷径

- 从归属不明或落后的旧/脏现场继续写，或把本地未提交内容当最新规范。
- 在没有项目声明基线和准确候选时开 PR、合并或安装。
- 用一次测试绿灯、截图、PR merge 或健康检查替代更高层验收。
- 由实现者自述替代独立审查，或因为等待 reviewer 就永久停滞。
- 将未合并 candidate 当正式版本，或静默安装较低 build。
- 自动删除 dirty、owner 不明或含 unknown 证据的现场。
- 用新增规则、台账、审批或更长文档掩盖自动化门禁或根因修复的缺失。

## 按风险裁剪

- 只读解释、调研和纯草稿：不触发实现门禁。
- 文档-only：检查链接、渲染和版本一致性；涉及规范决定时仍需独立审查。
- 小型、可逆、单模块且无共享合同/持久化/安装/安全边界：定向自动检查和 diff 审查即可，不要求全套发布矩阵。
- 行为改变、共享合同或用户可见路径：完整代码审查和分层验证。
- 安装、迁移、认证、安全、不可逆数据或高风险运行：独立高风险评审、回滚/补偿和真实环境验收。

## 安装与升级

本 Skill 的源文件在 GSE 仓库 `skills/professional-engineering-baseline/`。更新后用 `install-manifest.json` 记录文件 SHA-256，并运行：

```bash
python3 scripts/verify_engineering_skills.py \
  --target-root "$HOME/.agents/skills" \
  --target-root "<other-skill-root>/skills"
```

校验失败、manifest 缺失、GSE 路由链接断开或任一目标文件哈希不一致时，按 `blocked(baseline-missing)` 处理，不继续受影响的实现、部署或发布。
