# 修改影响与设计取舍

用于改变接口、协议、持久化、共享状态或跨组件行为的任务。局部修复沿用明确设计，只验证受影响行为；调用另一个函数本身不需要多方案设计。

## 修改影响：证明关键事实

先读真实候选、版本及调用路径。用一句话说清“这次修改安全，依赖哪个事实成立”。可能有多个事实，按风险选择需要证明的项，不强行把独立风险合成一个结论。

越过符号搜索能看到的边界：序列化字段、数据库列、旧文件、另一语言的读取端、后台任务、生命周期／并发时序、部署中的旧版本、功能开关。核验依赖锁定版本及本地补丁。没有搜索命中不能证明没有消费者；写出检查范围。

对关键事实给出与声称相称的证据：源码位置与时序推演、调用真实实现的定向测试、实际运行入口及结果读回。优先构造能推翻假设的输入，不能用重写同一算法的测试充当证明。脚本放在项目允许的输出位置；只有确有回归价值才保留为仓库测试。

结论分开记录已证实风险、已排除风险和未证实假设。每项指向候选、证据及失败后果。无法证明的假设继续验证、修复或协调必要条件，不以一份影响分析报告代替原交付。

## 设计取舍：从调用者出发

只有存在会显著影响行为、维护成本或不可逆迁移的取舍时，才比较结构不同的候选。先写真实调用用法和领域状态，再推导类型、接口、数据归属及模块边界。常规成熟方案、已有用户决定和明确的小修不重新竞赛。

比较最有竞争力的候选，通常两种即可；说明各自如何满足同一约束、需要迁移哪些消费者、验证难度和实际成本。候选不能只是同一设计的改名，也不为了凑数实现多份完整产品。能用短实验判定的事实通过实验解决；产品目标、用户偏好和授权不能由性能实验代替。

并行探索仅在收益大于启动与整合成本时采用，遵守项目 writer 规则。默认保留当前已确认模型；不因读本文件更改模型或创建新 chat。独立只读方案可交给临时子代理，最终实现保持一个 owner。

选定后说明选择依据及必要迁移条件，再实现和验证。反复出现相同逃逸类型、跨层知识或特殊分支时，检查设计前提；只重做受影响部分。删除内部旧 API 前确认消费者已经迁移；外部兼容合同需明确兼容范围、版本切换与退役条件，不照搬“全部立即删除”。

简短输出足以交代：关键事实及证据、影响边界、必要候选与取舍、实际验证和剩余依赖。无需每次生成独立报告。方法来源见 [来源说明](method-sources.md)。
