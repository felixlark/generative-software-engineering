# 内置 EGM：带上下文的负责人与独立的新读者

主 Agent（Elephant）保存原始意图、事实、决定和结果责任；Goldfish 从独立对话上下文读取稳定候选，发现读者理解、设计与执行缺口。核心流程为澄清、起草、审视、裁决修订、复审和交付。

这是 GSE 对 EGM 的内置适配。用户显式调用原插件的 interactive/full pipeline 时遵循该插件合同；本文件拥有 GSE 内部的触发、比例与收敛规则。

## 触发与比例

- 创建或实质改变可执行方案、架构、迁移、权限／数据完整性流程或其他高影响决策时，在依赖该决定的执行前评审。原有有效候选及决定直接复用。
- 已明确的小修、成熟 runbook、纯事实回答、格式调整由 owner 直接检查与验证；出现重要新假设或影响扩大时再评审。
- 常规方案一个只读 Goldfish，侧重执行就绪；跨组件、架构或高影响方案增加一个独立设计批评者。按风险选读必要材料，避免重复面板。
- 本流程审查方案与执行就绪；代码候选、正式回报和运行验证各有适用范围，按[协作规范](https://github.com/felixlark/generative-software-engineering/blob/main/docs/COLLABORATION.md#review-scope-and-evidence-reuse)分别办理。代码正确性疑点转成定向执行证据；用户、适用项目合同或具体高风险缺口要求候选级代码审查时读[独立审查](independent-review.md)，保留现有用户指定及平台强制检查。
- 同候选、环境、范围与独立性均有效的审查证据可覆盖其已核验的多个入口要求，包括方案与正式回报中的对应主张；加载本技能、EGM 插件或工程模板不重复开面板。未覆盖项明确保留，实质变化只复核受影响结论。

## 1. 固定可读候选

复用原设计、issue 或工作记录，写清用户目标、当前事实、范围、约束、授权、必要取舍、执行步骤、依赖及可观察验收。重要未知标明证据与处理方式。只有存在影响目标、成本、可逆性或重要风险的可行选择时比较方案。小方案保持简短；较长产物存项目允许的 artifact／日志位置。

提供目标文件的绝对路径、语义范围、候选身份、必要来源和标准。活跃 writer 与审查互斥：评审期间冻结有关文件，或提供完整稳定快照及相对依赖；哈希仅在需要校验身份时使用。每轮重新解析语义范围与行号。评审不读取临时写入中间态。

## 2. Fresh-context Goldfish

使用宿主原生子代理能力：有 `fork_turns` 时显式设为 `none`，有 `fork_context` 时显式设为 `false`；按实际工具 schema 调用。每位 reviewer 都用新上下文，沿用任务已确认的模型／强度，读候选、分配的标准和全部指定来源。只传原始要求和可读决定；作者私有推理、预期答案、完整聊天及个人 memory 留在作者侧。

共享 checkout 的 Goldfish 仅可读；写入、暂存、安装和发布由主 Agent 负责。对话隔离与文件系统／宿主规则隔离分别记录；工具未强制只读时记录行为约束。工具失败可沿支持入口重试一次；再次失败、缺失必要读取或没有实际返回报告，标记该 reviewer 为 not run，本轮状态为 incomplete。沿原任务修复工具或报告具体阻塞，保留可独立推进的授权工作。以 self-check 交付时明确标识，评审状态保持 incomplete。

### 内置角色与审查标准

| 角色 | 必读检查点 |
| --- | --- |
| 执行就绪 | 陌生执行者能找到当前入口和受影响文件；重大设计决定明确；必要步骤、消费者迁移、权限、依赖、恢复及验收具体可执行。常规实现细节由实现者决定。 |
| 设计批评 | 用户价值、范围、关键不变量与事实假设；有意义的替代方案和取舍；跨边界兼容、数据完整性、未知副作用、成本及故障恢复；验证覆盖真实结果。 |
| 理解检查（完整审视时） | 单独读候选，复述目标、范围、关键决定、执行路径与验收；指出理解所必需的缺失信息。主 Agent 对照原要求发现信息丢失。 |

下发内容包含角色、以上适用标准、模式、完整候选及来源列表、只读范围。要求每个发现给出 severity（Blocker/Major/Nit）、位置、缺失事实或错误假设、触发条件、可观察后果、证据和具体修订方向；允许零发现，避免假设缺陷配额。报告须确认实际读取的候选身份及材料，缺失读取单列。

完整审视保留五个视角及顺序：初始目标全景 → 单独读文理解 → 设计批评 → 对照原目标的中期全景 → 执行就绪。前三者检验目标与方案，后两者检验修改后的方向与实施条件。按语义分开方案与实施范围；日常按风险选择这些视角，用户明确要求原插件五阶段时走其完整流程。

## 3. Elephant 裁决与修订

汇总去重，给发现稳定 ID，保留原 severity、来源和候选；逐项裁决：

- **PROPOSE FIX**：有效且属当前范围，实施必要修订和受影响验证。
- **CONTEST**：附 reviewer 可访问的文件、合同或实验反证。
- **ESCALATE**：缺少用户独有事实、授权，或需要实质改变范围／成本／风险决定；提出最小必要问题，仅暂停依赖步骤。
- **DECLINE**：记录收益较低的 Nit。重要风险的接受由有权的用户或 owner 决定，相关授权和残余影响明确留证。

陌生读者的理解缺口应补进候选。已裁决事项再次出现时核对同一范围与依据；应用过的修订若再次失败则重开。评审意见是待核实发现；验证已确认的 Blocker/Major 仅阻塞依赖其成立的步骤。

沿用已有实施授权，在范围内修订并继续；用户明确要求逐项确认或只读评审时遵守该边界。原插件单独调用的确认门按原合同执行。重大取舍、额外成本及外部高影响动作按相应授权处理。

## 4. 复审与停止

常规一次初审加必要的 fresh-context 定向复审。重大修订覆盖变化及受影响依赖，复用其余有效证据；细微措辞修订由 owner 检查。

明确请求“迭代评审／打磨至收敛”时，每轮 fresh-context 读取当前稳定候选，保留相同必要标准与覆盖范围。轮次是否 clean 针对本轮输入候选、在应用本轮修订前判断：所有必需 reviewer 均完成，且本轮每个 Blocker/Major 均已凭可读反证 CONTEST 关闭，或残余重要风险已获对应授权接受。有效且需修复的 Blocker/Major（含 PROPOSE FIX）使本轮保持 non-clean；修订须进入下一轮稳定候选复审。两轮连续 clean 才记为 converged；失败或未运行的 reviewer 使本轮 incomplete。重要修订使受影响覆盖的连续计数重置。

五轮为成本复核点。若仍有重要开放项，或修订互相反转产生 churn，记录开放项、证据及成本原因，重新检查共同前提；仅在真实范围、风险接受或额外成本决定需要用户时提问。尚有授权内可执行修复时继续原任务，状态保持 open，后续轮次保留审计记录。轻微风格分歧列为 Nit，由 owner 裁决。

## 5. 带着证据交付

记录候选、reviewer 实际状态、标准和读取范围、发现及裁决、修订、复审结果和真实验收。模型 ID／总 token 若工具未提供则标未知，避免推断多模型或成本收益。较长报告留在原案，向用户只报告结果、实质变化、残留项及有用链接。

评审完成后，按原始任务实施、集成、安装和真实验收。只读任务返回评审结果。来源及许可证见[方法来源](method-sources.md)。
