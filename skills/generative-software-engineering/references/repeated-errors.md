# 重复错误治理

用于同类工程错误已重复发生，或用户明确要求治理反复纠正的问题。先从当前项目的失败、回退、评审和用户反馈中核验错误实例；只读获准范围，不跨项目挖掘个人聊天。没有重复证据时处理当前错误，不制造通用规则。

## 找到能阻止错误的位置

按失效机制归类，而非按措辞统计。保留具体实例、影响与原规则为何没有阻止它。优先选择能在当前范围解决问题且成本合理的层：

1. 数据与职责结构：消除重复真源，明确状态 owner，关闭错误入口；不要因一个错误擅自重构整个项目。
2. 类型／边界：让非法状态不能构造，或在外部输入处有明确拒绝与错误信息。
3. lint／构建／CI：自动识别已知错误，报错指向正确用法。历史存量可按增量约束，不能顺带批量清理。
4. 行为测试：从消费者入口验证错误后果，覆盖真正回归，而非检查文档措辞或复制实现。
5. 文档：保留必须由人或 Agent 判断的事项，说明原因和验证入口，不把可自动检查的问题继续变成长规则。

层级用于选择，不要求逐层实施；记录为什么所选层足够，只有实际需要才构建新工具。保留解释外部合同、非显然约束的注释，不自动删注释来追求数量。

## 证明约束有效

在隔离的受控样例中重放真实历史错误，让新检查确实失败；再运行正确样例与修复后的用户路径，证明不会把合法行为一起封死。不要为了验证破坏生产。记录错误样例、拒绝信号、正确样例和实际命令结果；本地与 CI 适用时应使用同一检查入口。

将约束与证据记在原问题或项目已有工程文档：错误类别 → 实际执行约束 → 验证入口 → 仍需判断的边界。只有代码完整替代旧规则且调用者已检查时才移除冗余文字，不清理无关历史或默写个人 memory。例外沿用项目审批规则，记录范围和退役条件。

修改约束按普通软件变更验证与交付，不因为“学习”自动扩大权限或启动监控。方法来源见 [来源说明](method-sources.md)。
